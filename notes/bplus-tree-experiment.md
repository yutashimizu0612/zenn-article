## 実験の題材

アクセスログの記録日時を検索する。

```sql
CREATE TABLE access_logs (
    log_id       bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    requested_at timestamp NOT NULL,
    path         text NOT NULL
);

CREATE INDEX access_logs_requested_at_idx
    ON access_logs (requested_at);
```

検索例：

```sql
SELECT *
FROM access_logs
WHERE requested_at >= TIMESTAMP '2026-04-08 10:00:00'
  AND requested_at <  TIMESTAMP '2026-04-08 10:05:00'
ORDER BY requested_at;
```

実際に使用する検索範囲は、リーフページの境界を観察してから決める。最初から日時を固定せず、複数のリーフページにまたがる範囲を選ぶ。

## 現時点での理解

### ルートノードと内部ノード

論理的には、検索先を選択するための次の情報を持つ。

- 区切りキー
- 子ページへの参照
- 最も左側の子ページへの参照

区切りキーはインデックス対象カラムと無関係な管理用の値ではなく、`requested_at`の値をもとに作られる。ただし、リーフにある通常の検索キーとは役割が異なり、下位ページへの経路を選択するために使われる。

### リーフノード

論理的には、次の組み合わせを持つ。

- 検索キーである`requested_at`
- 対応するテーブル行への参照

また、同じ階層の隣接するリーフページへの参照を持ち、範囲検索では次のリーフページへ進める。

### テーブル

インデックスとは別に存在する。インデックス上で`requested_at`が順序付けられていても、テーブル行が同じ順序で物理配置されているとは限らない。

## 実験上の注意

### 概念図と物理形式を混同しない

概念図では理解しやすいように「区切りキーと子参照」を単純化している。PostgreSQLの実ページには、通常のエントリ以外に、ページ境界や走査に必要な特殊な情報が含まれる可能性がある。

実際の出力が概念図と異なって見えた場合は、すぐに概念図が誤りだと判断せず、各項目の役割を確認する。

### `EXPLAIN`だけではアクセスしたページ番号は分からない

`EXPLAIN (ANALYZE, BUFFERS)`からは、インデックスが使用されたことと読み込んだバッファ数を確認できる。しかし、ルートからどのブロック番号をどの順番で読んだかは表示されない。

そのため今回の実験では、次の二つを組み合わせる。

1. `EXPLAIN`で対象インデックスが実際に使われたことを確認する
2. `pageinspect`で同じ検索条件の経路を手作業でたどる

「実行時の全ページアクセスをトレースした」とは表現しない。

### 実験中にインデックスを更新しない

データの追加や削除、インデックスの再作成によって、ルートや各ページのブロック番号、区切りキーは変わり得る。観察を始めた後は、ひとまとまりの記録が終わるまでデータとインデックスを変更しない。

### 2026-09-08：ルートノードの中身を理解する

#### 現在の到達点

ルートノード1個の中身を観察し、キーと子ページ参照の意味を整理した。子となる内部ノードの中身はまだ観察していない。

#### 実行したSQLと結果

DBeaverで実行した。

```sql
SELECT root, level
FROM bt_metap('public.access_logs_requested_at_idx');
```

結果は`root = 290`、`level = 2`。

- `root = 290`：このインデックスのブロック290がルートノード。
- `level = 2`：リーフを0として数えるため、ルート（2）→内部（1）→リーフ（0）の3階層。

続いて、そのルートの中身を取得した。

```sql

FROM bt_page_items('public.access_logs_requested_at_idx', 290);
```

出力の主要な列を抜き出すと次のとおり。

| itemoffset | ctid | itemlen | data |
|---:|---|---:|---|
| 1 | (3,0) | 8 | 空 |
| 2 | (289,1) | 16 | 00 b8 8a 93 44 d3 02 00 |
| 3 | (575,1) | 16 | 00 f0 40 a8 f0 d8 02 00 |
| 4 | (860,1) | 16 | 00 28 f7 bc 9c de 02 00 |
| 5 | (1145,1) | 16 | 00 60 ad d1 48 e4 02 00 |
| 6 | (1430,1) | 16 | 00 98 63 e6 f4 e9 02 00 |
| 7 | (1715,1) | 16 | 00 d0 19 fb a0 ef 02 00 |
| 8 | (2000,1) | 16 | 00 08 d0 0f 4d f5 02 00 |
| 9 | (2285,1) | 16 | 00 40 86 24 f9 fa 02 00 |
| 10 | (2570,1) | 16 | 00 78 3c 39 a5 00 03 00 |

この10行は10個のルートノードではなく、1個のルートノードに格納されている10個のエントリ。
`itemoffset`はページ内のエントリの位置番号で、物理的なバイト位置ではない。

#### 疑問1：dataはインデックス対象カラムの値か

今回の`data`に含まれるキーは、インデックス対象の`requested_at`の日時。
データに含まれる日時のうち、木を構築した結果、区切りとして選ばれた値という理解。

最初から特定の日時が区切りになると決まっているわけではない。ただし、選ばれた後は「どの子ページへ進むかを判断する」という役割を持つ。

#### 疑問2：なぜバイト列で表示されるのか

`pageinspect`が、保存内容を日時に変換せず、バイト列の16進数表記で表示するため。
区切りキーだから特別にバイト列に変換されたわけではない。

今回のPostgreSQLの`timestamp`は、内部では2000-01-01 00:00:00を基準にしたマイクロ秒数を8バイトの整数で保持する。
通常のSQLでは、この内部表現を人間が読める日時に変換して表示する。

今回の実行環境のバイト順（リトルエンディアン）に従って変換すると、2行目は次の対応になる。

```text
保存内容の16進数表示：00 b8 8a 93 44 d3 02 00
日時としての表示：   2025-03-14 04:24:00
```

日時への変換は会話中に補助計算で確認した。DBeaverで日時へ変換するSQLはまだ用意していない。

#### 疑問3：(289,1)の1は何か

今回のルートエントリでは、次の意味。

| 部分 | 意味 |
|---|---|
| 289 | 子ページのブロック番号 |
| 1 | このエントリに保持されているキーの列数 |

今回は`requested_at`の1列を保持しているため、後ろの値が`1`になっている。
「289ページの1行目」という意味ではない。

`ctid`という同じ欄名でも、ここでは子となるインデックスページへの参照を格納している。
テーブル行への参照としての`ctid`と混同しない。また、後ろの数値には一般にはフラグなども符号化されるため、どのページのどのエントリでも単純に列数として読めるわけではない。

#### 最初の(3,0)だけdataが空なのはなぜか

最も左側の子ページへの参照だから。
子ページ3への参照は保持するが、区切りキーは保持していないため、`0`になっている。

最初の区切りキーより小さい日時を探す場合に、この子へ進む。
今回のルートには、区切りキー9個と子ページへの参照10個が格納されている。

#### 現時点での理解

2行目のエントリは、「区切りとなる日時2025-03-14 04:24:00」と「子ページ289への参照」の組み合わせ。
担当範囲そのものが保存されているのではなく、区切りキーの比較で参照先を選ぶ。

参照： [PostgreSQL公式・B-treeページ調査関数](https://www.postgresql.org/docs/18/pageinspect.html#PAGEINSPECT-B-TREE-FUNCS)

#### `Buffers`と`Heap Blocks`の読み方

PostgreSQLにおける`heap`は、通常のテーブルデータを格納する方式・領域を指す。プログラムのメモリ管理でいうヒープとは別の意味。

今回の実行結果は、次のように読める。

```text
インデックス側のバッファアクセス：  5
テーブル側で処理したheapブロック：370
Bitmap Heap Scan以下の累積値：      375
```

`shared hit`は、必要なブロックがPostgreSQLの共有バッファに存在し、そこから利用できたことを示す。`shared read`なら、共有バッファになかったブロックを読み込んだことを示す。OS側のキャッシュもあり得るため、`read`を常に物理ディスクアクセスと同一視しない。

`Buffers`は重複を除いたページ番号の一覧ではなく、バッファアクセスの回数。また、上位ノードの値には子ノードの値が含まれる。次の値を足して755と数えてはいけない。

```text
Sort:              shared hit=375
Bitmap Heap Scan: shared hit=375
Bitmap Index Scan: shared hit=5
```

最上位の375がクエリ全体の累積値。今回の5という値は、手作業で確認した「ルート290 → 内部289 → リーフ286 → 287 → 288」と整合するが、実行計画にはブロック番号が表示されない。`shared hit=5`だけから、これら5個の固有ページを各1回読んだと断定はしない。

`Heap Blocks: exact=370`は、370件を1件ずつ検索した回数ではない。対象行が存在したテーブルページの数。同じページに複数の対象行があれば、対象行数より小さくなる。

```text
100件が2ページに集中   → Heap Blocks: exact=2になり得る
100件が100ページに分散 → Heap Blocks: exact=100になり得る
```

今回のデータはテーブル上で日時順に配置されていないため、370件が370個のテーブルページに分散していた。

#### Bitmap Scanと通常のIndex Scanの違い

今回、4件だけをリーフ286と287から取得する次の条件でも、オプティマイザはBitmap Scanを選択した。

```text
2025-03-14 10:28:00以上、10:32:00未満
```

```text
Bitmap Index Scan: shared hit=4
Heap Blocks: exact=4
Bitmap Heap Scan以下: shared hit=8
```

Bitmap Scanは、インデックスから行位置を集め、テーブルページの物理順にまとめてから取得する。この段階でB+Treeのキー順は結果の順序として維持されないため、今回の`ORDER BY requested_at`には別の`Sort`が追加された。

比較のため、トランザクション内だけBitmap Scanを候補から外した。

```sql
BEGIN;
SET LOCAL enable_bitmapscan = off;

EXPLAIN (ANALYZE, BUFFERS)
SELECT *
FROM public.access_logs
WHERE requested_at >= TIMESTAMP '2025-03-14 10:28:00'
  AND requested_at <  TIMESTAMP '2025-03-14 10:32:00'
ORDER BY requested_at;

ROLLBACK;
```

結果は通常の`Index Scan using access_logs_requested_at_idx`になった。B+Treeのキー順に行を取得できるため、別の`Sort`は現れなかった。

これは比較のために計画候補を制御した実験。通常時にPostgreSQLが選んだ計画はBitmap Scanだった。

#### Seq Scanとの関係

検索対象が増えて、該当行がテーブルの大部分のページへ広がると、インデックスから行位置を集める利点が小さくなる。その場合、オプティマイザはテーブル全体を順に読む`Seq Scan`を選ぶ可能性がある。

`Heap Blocks: exact`はBitmap Heap Scan固有の表示なので、Seq Scanでは通常表示されない。Seq Scanがアクセスしたバッファは、そのSeq Scanノードの`Buffers: shared hit/read`で確認する。
