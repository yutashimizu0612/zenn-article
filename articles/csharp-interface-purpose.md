## インターフェースとは

<!--
この章全体で伝えること。

- インターフェースは、利用側と実装側の境界に置かれた契約である
- 利用側と実装側のどちらにとっても同じ契約である
- ただし、利用側には「利用できる操作」、実装側には「提供すべき操作」として見える
- C#の interface は、その契約を型として表す仕組みである
- 差し替え、テスト、ポリモーフィズムなどのメリットは、後の章で説明する
-->

### エアコンを例にインターフェースのイメージを掴む

<!--
この節の役割は、「境界面」の感覚を日常的な例から得ること。

- interface は、一般に物事が接する境界や接点を意味する
- エアコンには、利用者向けに次のような操作が公開されている
  - 電源を入れる、切る
  - 設定温度を変える
  - 運転モードを変える
  - 風量を変える
- 利用者は、リモコンやスマートフォンのアプリを通じて操作する
- 利用者が知る必要があるのは、どのような操作が用意されているかである
- ボタンを押した後、内部で何が起きるかを知る必要はない
  - 温度をどのように検知しているか
  - コンプレッサーをどのように制御しているか
  - 風量をどのように調整しているか
- 利用者に操作を公開することは、その操作に対応する機能を提供すると約束することでもある
- 「温度を設定できる」と公開する以上、エアコン側には、設定された温度に応じて動作する仕組みが必要である
- 公開された操作は、利用者には「使える機能」、エアコン側には「実現すべき機能」として見える
- 公開された操作が、利用者とエアコンの接点になる
- インターフェースによって、利用する側と内部の仕組みが隔てられている

この節では扱わないこと。

- コンパイルエラーなどのC#固有の仕組み
- ポリモーフィズム
- 実装の差し替え
- 依存性逆転
- 「インターフェースがなければ内部を直接操作する」という極端な仮定
-->

インターフェース（interface）とは、物事と物事が接する境界や接点のことです。

身近な例として、エアコンを考えてみます。エアコンには、「電源を入れる」「設定温度を変える」「運転モードを変える」「風量を変える」といった、利用者向けの操作が用意されています。利用者はリモコンやスマートフォンのアプリを通じてこれらを操作します。

利用者が知る必要があるのは、どのような操作が用意されていて、それをどう使うかです。ボタンを押した後、エアコンが温度をどのように検知し、風量をどのように制御しているかといった内部動作を知る必要はありません。

一方、エアコン側から見ると、利用者向けに公開した操作は、それに対応する機能を提供するという約束です。「設定温度を変えられる」と公開する以上、エアコン側には、指定された温度に応じて動作する仕組みを用意しなければなりません。公開された操作は、利用者にとっては「利用できる機能」であり、エアコン側にとっては「実現しなければならない機能」です。

このように、利用者とエアコンの間には、利用者向けに公開された操作があります。この公開された操作が両者の接点、つまりインターフェースです。利用者はこの接点を通じて、内部の仕組みに触れることなくエアコンの機能を利用できます。

### ソフトウェア開発におけるインターフェース

<!--
この節の役割は、エアコンの例をC#のコードへ対応させること。

定義はMicrosoftの日本語版C#リファレンスに従う。

- 公式リファレンス: https://learn.microsoft.com/ja-jp/dotnet/csharp/language-reference/keywords/interface
- C#言語仕様: https://learn.microsoft.com/ja-jp/dotnet/csharp/language-reference/language-specification/interfaces
- 公式では、インターフェースはコントラクトを定義するものと説明されている
- そのコントラクトを実装するクラス、レコード、構造体は、定義されたメンバーの実装を提供する必要がある
- 記事では「コントラクト」を「契約」と表現する
- C#のインターフェースは、実装する型が提供すべきメンバーを契約として表す型である
- この記事では、最も基本的なメソッドとプロパティを扱う
- インターフェースは主に「何ができるか」を表し、「どのように実現するか」は実装クラスに置く
- 「メソッドやプロパティの宣言だけを並べた型」「インターフェースの実態は」という表現は使わない
- Javaには話を広げず、C#に限定する

サンプルコードは次の三つに絞る。

- INotifier
- EmailNotifier
- NotifyCompletion
- SmsNotifierは削除し、複数実装の説明は後のIPaymentMethodに任せる

コードについて説明すること。

- INotifierは、Send()を利用できるという契約を定めている
- INotifierには、メールの作成やSMTP接続などの処理は書かれていない
- EmailNotifierは「: INotifier」と書くことで、INotifierの契約を引き受けている
- INotifierにSend()が定められているため、EmailNotifierは契約に従ってSend()の具体的な実装を提供する
- INotifierが定めた「メッセージを送信できる」という契約を、EmailNotifierはメール送信という方法で実現している
- NotifyCompletionは通知機能の利用側である
- NotifyCompletionの引数はEmailNotifierではなくINotifierである
- NotifyCompletionは、渡されたオブジェクトの具体的な型を知らなくてもSend()を呼び出せる
- 実際に動作するオブジェクトは具象クラスだが、利用側のコードは具象型ではなく契約に依存している

この節ではコード上の登場人物と基本構造を提示するところまでにする。利用側と実装側からどう見えるかは、次の節で説明する。
-->

エアコンでは、利用者に公開された操作と、その操作を実現する内部動作が分かれていました。ソフトウェア開発でも同じように、機能を使う側が知る必要のある操作と、その機能を実現する内部の処理を分けて考えます。C#では、この関係を契約として表す仕組みとして[`interface`](https://learn.microsoft.com/ja-jp/dotnet/csharp/language-reference/keywords/interface)が用意されています。

`interface`は、利用できる操作を契約として定めます。これを実装すると宣言したクラスなどの型は、その契約に従って、定められたメンバーの実装を提供します。インターフェースが主に表すのは「何ができるか」であり、それを「どのように実現するか」は実装する型の責任です。

:::message
C#のインターフェースは、メンバーの既定の実装や静的メンバーなども定義できます。この記事では、メソッドの宣言に対して実装クラスが処理を提供する基本的な形を扱います。
:::

コードで確認してみます。

```cs
// インターフェース：メッセージを送信できるという契約を定める
public interface INotifier
{
    void Send(string message);
}

// INotifierの契約に従い、メール送信として実装する
public class EmailNotifier : INotifier
{
    public void Send(string message)
    {
        // 宛先を組み立て、SMTPサーバーに接続し、本文を整形して送信する…
        // といったメール送信に関する実装詳細がここに入る
        // 通知機能を利用する側が知る必要のない内部実装
    }
}

// 通知機能を利用する側
public void NotifyCompletion(INotifier notifier)
{
    notifier.Send("処理が完了しました");
}
```

`INotifier`は、「メッセージを送信する」という契約を`Send()`として定めています。ここには、宛先をどのように組み立てるか、どのようにSMTPサーバーへ接続するかといった具体的な処理は書かれていません。

`EmailNotifier`は、`INotifier`を実装すると宣言することで、その契約を引き受けています。`INotifier`に`Send()`が定められているため、`EmailNotifier`は契約に従って`Send()`の具体的な処理を提供します。`INotifier`が定めた「メッセージを送信できる」という契約を、`EmailNotifier`はメール送信という方法で実現しているわけです。

`NotifyCompletion`が利用しているのは、具象クラスの`EmailNotifier`ではなく`INotifier`です。引数も`INotifier`として受け取っているため、`NotifyCompletion`は`EmailNotifier`を知りません。エアコンの利用者が内部動作を知らず、リモコンに用意された操作だけを使うのと同じように、`NotifyCompletion`は`INotifier`に公開された`Send()`だけを呼び出しています。

### 利用側と実装側では見え方が異なる

<!--
この節は第1章の中心となる説明。

- インターフェースは、利用側と実装側のどちらにとっても契約である
- INotifierの定義自体は一つだが、契約のどちら側に立つかによって見え方が異なる
- (warning ブロックで)ここでいう利用側と実装側は、開発者やチームの区分ではなく、コード上の立場を表す
- (warning ブロックで)同じ開発者が両方のコードを書く場合でも、それぞれの立場からインターフェースを見ることができる

利用側から見た説明。

- 利用側はNotifyCompletionである
- 利用側に見えているのは、INotifierに定められた操作である
- INotifierは「どのような操作を呼び出せるか」を示すメニュー表のようなものである
- 利用側はSend()を呼び出せるが、その内部処理を知らない
- EmailNotifierにINotifierにはない独自のメンバーがあっても、INotifierを通じて利用するコードからは見えない
- 利用側が依存しているのは、EmailNotifierの持つすべての機能ではなく、INotifierに公開された部分だけである
- エアコンの例では、利用者がリモコンに用意された操作だけを見ることに対応する

実装側から見た説明。

- 実装側はEmailNotifierである
- EmailNotifierは「: INotifier」と書くことで契約を引き受ける
- 実装側から見ると、INotifierは「提供しなければならない操作の一覧」である
- INotifierにSend()が定められているため、EmailNotifierはSend()の実装を提供しなければならない
- Send()を実装しなければコンパイルエラーになる。INotifierが提示する契約を実現していないので当然
- コンパイラが確認するのは、必要なメンバーが提供されているかである
- Send()が意味的に正しく通知するかまでは保証しない

「インターフェースは実装を強制する」という説明の位置づけ。

- 「インターフェースは実装を強制する」という説明は間違いではない
- ただし、それは実装側から見た特徴を述べたものである
- 利用側の視点が抜けると、「境界面」と「実装の強制」という説明のつながりが分かりにくくなる
- 契約にSend()が定められている以上、その契約を実装すると宣言した型はSend()の実装を提供しなければならない
- 「利用側が安心して呼び出せるようにするため」といった目的は付け加えず、契約と実装の関係として説明する

節のまとめ。

- 同じインターフェースが、利用側には「呼び出してよい操作の一覧」、実装側には「提供しなければならない操作の一覧」として見える
- インターフェースを読むときは、今見ているコードが利用側なのか実装側なのかを考える
- 第2章でも、この二つの視点から実際のインターフェースを確認する
- h4には分割せず、一つのh3の中で段落を切り替えて説明する
-->

## nopCommerceの実例からインターフェースの使われ方を見る

<!--
各実例を次の観点から確認する。

- 利用側は誰か
- 利用側には何が見えているか
- 実装側は誰か
- 実装側には何が要求されているか
- 契約をインターフェースとして表さなかった場合、何が変わるか
-->

### 複数の支払い方法を共通に扱う `IPaymentMethod`

<!--
- 利用側は、具体的な支払い方法を知らずに決済処理を呼び出す
- 決済プラグインには、決済手段として必要な操作の提供が要求される
- 複数の決済実装を同じ契約で扱える
- 新しい支払い方法を追加しやすい
- 実装の選択や条件分岐が消えるとは限らず、プラグイン管理などの組み立て側へ移る
- ポリモーフィズムと実装追加のしやすさが特に表れている
-->

### メール送信の実装詳細を隔てる `IEmailSender`

<!--
- 利用側は、メールを送信できることだけを知る
- 実装側には、メール送信機能の提供が要求される
- SMTP接続やMIMEメッセージの組み立てなどは実装クラス側に置かれる
- 本番実装が一つでも、外部処理との境界として意味がある
- 具象クラスへ依存する場合と比べて、テスト用実装へ差し替えやすい
- 実装詳細からの分離とテスト時の差し替えが特に表れている
-->

### 異なる型を共通の役割で扱う `IStoreMappingSupported`

<!--
- nopCommerceでは、商品、カテゴリ、ブログ記事などをストアごとに表示制限できる
- 利用側は、具体的なエンティティの種類ではなく「ストアごとの制限に対応している」という契約を見る
- 実装する型には LimitedToStores プロパティの提供が要求される
- IStoreMappingServiceは、異なるエンティティを同じ契約で扱う
- 実装の差し替えを主目的としたインターフェースではない
- 複数の型を共通の役割で扱えることが特に表れている
-->

### 実例によって目立つ効果が異なる

<!--
- どの例でも、インターフェースは利用側と実装側の間の契約である
- ただし、インターフェースを設けた設計上の狙いは異なる
- IPaymentMethodでは、複数実装の追加や差し替えが中心
- IEmailSenderでは、外部処理の詳細から利用側を切り離すことが中心
- IStoreMappingSupportedでは、異なる型を共通の役割で扱うことが中心
- 別種類のインターフェースではなく、同じ仕組みから異なる効果が表れている
-->

## インターフェースを利用するメリット

<!--
新しいコード例は増やさず、直前の三つの実例を一般化して整理する。
-->

### 実装の詳細から利用側を切り離せる

<!--
- 主に IEmailSender を振り返る
- 利用側は「何ができるか」に依存し、「どう実現するか」を知らずに済む
- 具象クラスの実装詳細や変更が利用側へ波及しにくくなる
-->

### 異なる実装や型を同じ契約で扱える

<!--
- IPaymentMethodでは、異なる決済実装を同じ決済手段として扱う
- IStoreMappingSupportedでは、異なるエンティティを同じ役割で扱う
- 実装ごとの条件分岐を利用側から分離できる
- クラス継承とは別に、一つの型へ複数の契約を持たせられる
-->

### 契約を満たす実装へ置き換えやすい

<!--
- 同じ契約を満たす実装を追加しやすい
- テスト用実装へ差し替えやすい
- 必要なメンバーの実装漏れをコンパイル時に検出できる
- 処理内容が意味的に正しいことまで保証するものではない
-->

### 必要な境界があるときに使う

<!--
注意点は主軸にせず、短くバランスを取る。

- インターフェースを作ること自体が目的ではない
- 隠したい実装詳細や、共通に扱いたい実装・型があるときに効果を発揮する
- 具象クラスへ直接依存して問題がない場合は、インターフェースが構造を複雑にすることもある
- 何を境界として切り離したいのかを考えて使う
-->

- 実装側には「提供しなければならない操作の一覧」として見える
